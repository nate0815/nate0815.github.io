# 文件回填(doc-sync)

把這次的變動同步回 `doc/`。**先對規格,再回填** —— 順序不能反。

> 本檔是正本(放在工具中立的 `.agents/skills/` 下)。`.claude/skills/doc-sync/SKILL.md`
> 只是指回這裡的 stub,不要去改那份。
> 移植自 doc-system-kit 的 doc-sync,依本站的文件組成改寫:沒有 PLAN、DEVLOG 不拆檔、多一份給使用者看的 WORKFLOW。

## 0. 最重要的一條

`doc/DESIGN.md` 是**唯一參照**。任何程式或其他文件與它牴觸,預設是**那邊錯了**,不是 DESIGN 過時了。
**不得自行改寫 DESIGN 來遷就實作。**

---

## 1. 先撈原料、再對規格(一定先做這步)

### 1a. 原料在 commit body,不在 diff

```bash
git -c core.quotepath=false status --short -uall
git -c core.quotepath=false diff
git log --format='%h%n%B%n---' main..HEAD    # 在分支上時;⭐「為什麼」的來源
```

**回填的「為什麼」先從 commit body 抄,不要從 diff 反推。** commit body 是空的就直接問使用者理由,
不要寫一個看似合理的猜測。

### 1b. 對規格

拿變動內容逐項比對 `doc/DESIGN.md` 相關章節,特別是「明確不做的事」與「動態效果」。

| 誰跟 DESIGN 不一致 | 怎麼處理 |
|---|---|
| **程式/樣式/設定** | **停下來升報**(§2),等裁決 |
| **TECH/WORKFLOW/README** | 以 DESIGN 為準直接改對齊,收工回報裡列出改了哪幾處 |
| **DESIGN 自己要改** | 一定要使用者點頭。Claude Code 會跳確認框,那一框就是裁決點 |

---

## 2. 升報格式

發現實作與 DESIGN 牴觸時,給這張表加三個選項,然後**停下等回覆**:

```
⚠ 實作與規格不一致

| 項目 | DESIGN 怎麼寫 | 實作變成怎樣 | 出處 |
|---|---|---|---|
| (名稱) | 「章節標題」(原文) | (現況) | source/css/custom.css:NN |

要怎麼處理?
  1. DESIGN 是對的 → 我把實作改回去
  2. 實作是對的 → 你同意我改 DESIGN
  3. 都先不動 → 記進 DEVLOG 的待辦
```

---

## 3. 路由表

| 這次改了什麼 | 回填到哪 |
|---|---|
| **規格**:網站要長怎樣、要不要做某件事、配色、版面、動態效果 | ⚠ 需授權。改 `doc/DESIGN.md` 對應章節(就地改成新版,不留舊值),更新開頭的「最後更新」日期 |
| **決定不做某件事** | `doc/DESIGN.md`「明確不做的事」加一列,寫理由(需授權) |
| **程式/樣式/設定的做法**:新的 `scripts/`、檔案職責、部署流程 | `doc/TECH.md` 對應章節(「檔案結構與各檔職責」「部署流程」等) |
| **踩到的坑** | `doc/TECH.md`「已知的坑」:寫「現象 → 原因 → 解法」,缺一不可。用看得到的現象當標題 |
| **使用者要做的操作變了**(發文、加作品、合併 PR) | `doc/WORKFLOW.md`。寫給剛接觸 git 的人看,步驟要能照做 |
| 檔案結構/怎麼跑起來變了 | 根目錄 `README.md`(只放指標,深度內容留在 `doc/`) |
| **任何一段工作(無例外)** | `doc/DEVLOG.md` **最上面**加一段:做了什麼/為什麼/踩到的坑/驗證了什麼/還沒做 |
| 待辦有了結論 | `doc/DEVLOG.md` 的待辦勾掉並註明日期,**不刪掉** |

**動筆順序**:先撈 commit body → 改正本(DESIGN 需授權/TECH/WORKFLOW/README)→ **最後**才寫 DEVLOG。順序反了會漏寫「為什麼」。

---

## 4. 護欄

| 護欄 | 說明 |
|---|---|
| DESIGN 衝突一律升報 | 不自作主張選邊 |
| 同一件事不寫在兩處 | 內容放對應正本,DEVLOG 只記「何時、為什麼」 |
| DEVLOG 只追加不改寫 | 舊段落就算被推翻也保留;推翻時在新段落寫清楚,並連回舊的 |
| 新寫的跨檔引用不寫章號 | `TECH「已知的坑」` ✅ / `TECH 第 3 節` ❌。章號位移不會有任何工具報錯。既有的不回頭改 |
| 判準寫名字不寫數量 | 「HAND SIGNAL 與 AFTERGLOW 是精選」✅ /「2 個精選」❌ —— 數字每加一項就要回頭改 |
| 用實際日期 | `date +%F` 取,不寫「昨天」「上週」 |

---

## 5. 收工回報

回報一張表,不要只說「已更新文件」:

| 文件 | 章節 | 改了什麼 |
|---|---|---|
| doc/TECH.md | 已知的坑 | 新增「xxx」 |
| doc/DEVLOG.md | 最上面 | 2026-10-18 這一輪的紀錄 |

沒動到的文件也講一句為什麼沒動(例如「規格沒變,DESIGN 不動」)。

---

## 6. commit 的時候要做的事(回填成本前移)

**做了任何有「為什麼」的決定,commit body 就要有 `決策:X/因為 Y`。**

```
feat(about): 加上 Ko-fi 贊助按鈕

決策:只放一般連結,不用 Ko-fi 的浮動小工具
因為:小工具每頁多載一支外部程式,而且一直浮在畫面上,違反 DESIGN「動態效果」
```

`因為` 要具體到能被反駁 ——「比較簡潔」等於沒寫。

| 情況 | 寫不寫 |
|---|---|
| 兩個做法選了一個 | **寫**,尤其寫沒選的為什麼不選 |
| 與使用者指示有出入 | **一定寫**,標 ⚠️,回填時原樣帶進 DEVLOG 與收工回報 |
| 踩了坑才繞過去 | **寫**「現象 → 原因」 |
| typo、換變數名 | 不用 |

commit body 不是 DEVLOG 的替代品,是它的原料。
